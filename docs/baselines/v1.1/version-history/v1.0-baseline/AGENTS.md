# AGENTS.md — QKH 项目执行规则

## 项目目标
建设企业质量统一知识中枢 V1.0。以证据可追溯、文件权威性、版本正确、权限隔离为优先级，不以 Demo 视觉或模型回答流畅度代替验收。

## 必读顺序
1. `README.md`
2. `PROJECT_PLAN.md`
3. `ARCHITECTURE.md`
4. 与当前任务对应的 `DATABASE_SCHEMA.md`、`API_SPEC.md`、`SECURITY.md`、`TEST_PLAN.md`
5. 当前阶段 `execution/PHASE-*.md`
6. 相关 ADR

## 强制工程规则
- 开始修改前检查 Git 状态、现有代码、依赖版本、环境变量和当前测试；不得覆盖用户现有文件。
- 先提出实施计划和受影响文件，再实施；按小步提交，避免一次性大改。
- TypeScript 使用 strict；API 输入输出使用 Zod；数据库变更使用迁移文件。
- 不把密钥、企业微信凭证、Dify API Key、真实员工数据写入代码、日志或测试样本。
- 不将原始文件内容、受限检索结果写入不受控日志。
- 所有文件、版本、条款、来源均使用稳定 ID；文件名不是主键。
- 不允许模型决定权限、权威状态、审批状态或文件有效状态。
- 权限过滤必须发生在检索结果进入 LLM 之前。
- 任何不确定权威版本的资料不得作为正式要求回答；需标记冲突/待确认并升级。
- 每个检索片段必须能追溯到原文件、版本、章节/条款及页码或工作表位置；无法定位时明确标注。
- 解析器输出需保留原始文件与解析产物，不得只保存切片文本。
- 不允许把用户反馈自动写入正式知识；反馈进入待审核队列。
- 不引入 GraphRAG、Neo4j、独立向量数据库或第二套完整 RAG 平台，除非 ADR 和基准测试证明必要。
- 不声称未执行的测试已经通过；报告命令、结果、未覆盖范围。
- 每个阶段结束更新 `CHANGELOG.md`、`records/CHANGE_RECORD.md`、`records/WEEKLY_PROGRESS.md`，并提交阶段验收报告。

## 开发流程
1. 检查现状与约束。
2. 列出任务拆分、风险、验收条件。
3. 实现最小变更。
4. 执行 lint、typecheck、unit、integration、安全测试。
5. 检查差异、迁移和敏感信息。
6. 更新文档和记录。
7. 汇报已完成、未完成、风险、下一步。

## 不可擅自决定
- OA/微盘数据源是否权威。
- 文件状态、有效日期和适用范围。
- 任何质量要求的专业解释。
- 员工权限和跨部门数据授权。
- 生产部署、数据迁移和删除操作。
